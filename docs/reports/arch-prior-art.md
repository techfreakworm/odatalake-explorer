# arch-prior-art

## Summary
Ask OLake research (2026-10-16/17): architecture evidence, prior art, likely judge probes and fast evaluation, plus proofs of concept (POCs) on the real OLake docs. I could not write report.md: the harness blocks report files from subagents, so the full report is in these fields.

1) Ingestion: crawl rendered HTML from the sitemap rather than raw MDX. 20 of 125 published pages render shared snippets through global <Component/> tags, so that text is missing from raw MDX (6 of the 20 are JSX config tables). Rendered HTML keeps hidden tab panels and gives every h2/h3 an anchor. Full crawl of 124 /docs/ pages: 69.7 s, 11.2 MB. Parse with lxml: the minified HTML omits </li> and </p>, and Python's html.parser mis-nests it.
2) Chunking: I built 1,541 heading-scoped chunks (p50 116, p90 400 est. tokens; about 270k tokens total) with breadcrumbs of page trail, tab label and h2/h3. Prepending the breadcrumb raised Hit@1 by 11-14 points for BM25, dense and hybrid on 44 hand-written questions. This agrees with Anthropic Contextual Retrieval (top-20 failure 5.7% to 3.7%) and dsRAG chunk headers (4.72 to 6.04).
3) Retrieval: hybrid BM25 + bge-small with RRF k=60 plus breadcrumbs scored best (Hit@1 0.864, Hit@3 0.977, Hit@5 1.0, MRR 0.921) and costs about 10 ms on CPU. Small open cross-encoders hurt Hit@1 (MiniLM 0.773, jina-turbo 0.750) and add about 1.1 s per 30 candidates on CPU. Vendor rerank gains (Microsoft +21 NDCG@3, Anthropic with Cohere 2.9% to 1.9%) need a hosted API and an A/B test first.
4) Honesty: a dense-score threshold separates off-topic questions perfectly (AUROC 1.0) but on-topic unanswerable ones only partly (AUROC 0.886). At 95% answer coverage only 36% of unanswerables are refused, so an LLM 'sufficient context' gate is needed. The Sufficient Context paper reports hallucination on insufficient context of 15-40% across models.
5) Citations: emit only canonical sitemap URLs taken from chunk metadata, and verify the [n] mapping on the server. olake.io has 285 client-side redirects whose old URLs return HTTP 200 with a meta-refresh page; missing pages return 404. Each deploy changes every page's ETag, so detect page changes by content hash.
6) Probable judge probes: unanswerable questions, false premises, version and deprecation questions (wal2json is deprecated), Go-vs-Fusion ambiguity (12 near-duplicate page pairs, up to 0.95 Jaccard), follow-ups, direct and indirect prompt injection, off-topic, citations that do not support the claim, broken links, latency and concurrency, empty or huge input, mobile layout, one-line embed.
7) Evaluation: a custom async scorer (deterministic checks plus one LLM-judge call per question) runs 70 questions in about 1-2 minutes at concurrency 8 if rate limits allow. promptfoo can call POST /ask directly, but needs --no-cache for live runs. RAGAS and DeepEval need the retrieved contexts and about 8 LLM calls per sample.
8) Ranking: B 'Recommended' 86/100 (A plus sufficiency gate, citation verification, streaming, cache, freshness, hardening) > C 'Ambitious' 67/100 (range 62-77, agentic plus long-context; high variance) ≈ A 'Simple fallback' 67/100. Build A first, then layer B.

Caveats: POC n=44 with one annotator and page-level gold. Vendor numbers are self-reported. Gemma 4 free-tier rate limits and JSON-schema support on the Gemini API are unverified. I made no edits to the git worktree; the uncommitted changes in poc/pyproject.toml and poc/uv.lock there are from other agents.

## Recommendations
- **Ingest rendered HTML from the sitemap (/docs/ first; blog as a lower-priority tier), parse with lxml or html5lib, keep hidden tab panels with their labels, rebuild code from div.token-line, and convert JSX config tables to 'key: description' lines** — Raw MDX misses shared-snippet content on 16% of pages. Minified HTML breaks html.parser. A full crawl is about 70 s, so frequent re-indexing is cheap. [evidence: measured: shared_usage.py, debug_tabs.py, crawl_docs.py; https://docusaurus.io/docs/api/docusaurus-config]
- **Chunk at h2/h3 with a soft cap of about 400-500 tokens and no overlap; never split inside fences; keep tables whole; prepend a breadcrumb (Docusaurus trail + [tab] + h2 + h3 + product tag Go/Fusion); store canonical URL, #anchor, lastmod, content hash and version; expand to the parent h2 section (up to about 1,200 tokens) at answer time** — The breadcrumb prefix gave +11-14 points Hit@1 at zero LLM cost. Chroma shows smaller chunks without overlap improve precision/IoU. dsRAG and Anthropic show gains from contextual headers. [evidence: measured: retrieval_eval.py; https://www.trychroma.com/research/evaluating-chunking; https://github.com/D-Star-AI/dsRAG; https://www.anthropic.com/news/contextual-retrieval]
- **Use hybrid BM25 + dense with RRF k=60 (top 100 each to fused top 8) as the default. Do not ship a small open cross-encoder; A/B a hosted reranker (Cohere v3.5/v4) only behind a flag after measuring on a 70+ question OLake gold set** — Hybrid plus breadcrumb was the best measured configuration (MRR 0.921). Small open rerankers reduced Hit@1 by 9-11 points and add about 1.1 s on CPU. Vendor reranker gains are real but unverified on OLake. [evidence: measured: retrieval_eval.py; http://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf; https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/final/en-us/microsoft-brand/documents/ai-search-query-engine-performance-whitepaper.pdf]
- **Abstention in two layers: (1) off-topic gate on dense top-1 score, recalibrated for the deployed embedding model; (2) LLM output field sufficient_context plus a rule that an answer with no surviving citation is refused. For unsupported features answer 'not in the documented list' and cite the list page; for false premises correct the premise** — The score gate separates off-topic questions perfectly but only 36% of on-topic unanswerables at 95% coverage. LLMs hallucinate 15-40% on insufficient context. CRAG scoring gives -1 for wrong answers and 0 for abstaining. [evidence: measured: abstain_probe.py; https://arxiv.org/html/2411.06037; https://arxiv.org/html/2406.04744v2; https://arxiv.org/html/2309.01431]
- **Citations: the LLM returns [n] markers plus used_ids; the server drops invalid ids, runs a cheap per-sentence support check, and builds 'sources' only from the used chunks' canonical sitemap URLs (exact sitemap form with trailing slash; anchors only in the UI); never emit model-written URLs** — olake.io returns 200 for 285 redirect stubs, so model-written URLs can look valid while being stale. The judges' URL matching is unknown. ALCE shows even strong models leave many statements unsupported. [evidence: measured: curl redirect stub and 404; https://arxiv.org/html/2305.14627; https://github.com/langchain-ai/chat-langchain/blob/master/src/tools/link_check_tools.py]
- **Latency and cost: exact-match answer cache keyed on normalised question + index version + model; no semantic answer cache; static prompt prefix first for provider caching; SSE streaming in the UI while POST /ask stays plain JSON; overall timeout of about 20 s with provider fallback on 429/5xx** — Semantic caches give wrong-answer hits on near-duplicate questions. Provider prefix caching cuts input cost by 90-95%. Perceived latency needs feedback within about 1 s. [evidence: https://github.com/zilliztech/GPTCache; https://arxiv.org/abs/2502.03771; https://platform.claude.com/docs/en/build-with-claude/prompt-caching; https://developers.openai.com/api/docs/guides/prompt-caching; https://www.nngroup.com/articles/response-times-3-important-limits/]
- **Freshness: scheduled re-crawl (e.g. hourly) driven by sitemap lastmod plus per-page content hash (not ETag); atomic index swap; expose the index timestamp and version in /healthz and the UI footer** — Every deploy changes every ETag and Last-Modified. A full rebuild takes about 70 s crawl + 13 s chunking + about 90 s CPU embedding. [evidence: measured: curl -I headers, crawl and embedding timings]
- **Production hardening: 400 on empty or non-JSON input; 413 or truncation above a size cap; per-IP rate limit; CORS for the docs origin; canary string in the system prompt with an output check; retrieved text treated as data; product disambiguation for Go vs Fusion near-duplicates; structured logs with request ids** — OWASP LLM01 covers direct and indirect injection via retrieved docs. The near-duplicate pages make ambiguity probes likely. Malformed and huge inputs are standard production probes. [evidence: https://genai.owasp.org/llmrisk/llm01-prompt-injection/; https://www.promptfoo.dev/docs/red-team/rag/; measured: near_duplicates.txt]
- **Embedding UX: a single defer-loaded script tag (web component or iframe) with data-api, full-screen on mobile, numbered citation chips that deep-link with #anchor, copy buttons on code, thumbs feedback; show the Docusaurus scripts[] snippet in the README** — One script tag is the norm (kapa, DocsGPT), and OLake's config already uses scripts[] with defer. kapa defaults to full-screen on mobile. [evidence: https://docs.kapa.ai/integrations/website-widget/configuration/legacy; https://docs.docsgpt.cloud/Extensions/chat-widget; https://docusaurus.io/docs/api/docusaurus-config]
- **Evaluation: a custom async scorer with deterministic checks (schema, allowlist, GET liveness with meta-refresh detection, #anchor check, gold-page hit, must/must-not regex, abstention regex, canary, 4xx on malformed input, p50/p95 latency) plus one LLM-judge call per question (A/B/C correctness, citation support, appropriate abstention), using a different model family at temperature 0. Hand-label 10-15 items to check judge agreement. Set mix for about 70 questions: 50-55 answerable, 10-15 unanswerable, 3-5 false premise, 3-5 version/deprecation, 3-5 follow-up pairs, 2-3 ambiguous Go/Fusion, 3-5 injection/off-topic, 2 malformed. Seed from data/gold_questions.json plus the 14 unanswerable and 6 off-topic questions in scripts/abstain_probe.py** — Runs in about 1-2 minutes at concurrency 8 if rate limits allow. Covers the probes in kapa, CRAG, RGB, MTRAG and OWASP. RAGAS/DeepEval need contexts and about 8 calls per sample. promptfoo is an alternative but needs --no-cache. [evidence: https://www.kapa.ai/blog/how-to-properly-evaluate-ai-assistants-for-technical-documentation; https://arxiv.org/abs/2306.05685; https://arxiv.org/abs/2406.12624; https://hamel.dev/blog/posts/evals/; https://www.promptfoo.dev/docs/usage/command-line/]
- **Architecture ranking (weighted score = sum of score x weight / 5; criteria accuracy 35 / citations-honesty 15 / production 20 / UX-embed 15 / engineering 15): (1) B Recommended scores 4/5/4/5/4 = 86; (2) C Ambitious (agentic/CRAG + multi-source + hosted reranker + Self-Route long-context fallback + claim-level NLI) scores 4/3/3/4/2 = 67, range about 62-77; (3) A Simple fallback (crawl + breadcrumb chunks + hybrid RRF + one LLM call with [n] citations + FastAPI + basic widget) scores 3/3/4/3/4 = 67. Build A first as the safety net, then add B features in rubric-weight order: sufficiency gate and citation verification; streaming, embed and mobile; cache, freshness and hardening; CI eval** — B targets every rubric line at about one LLM call per question. C's upside (long context beats RAG on average; hosted rerankers) is offset by measured reranker regressions, 3-6 LLM calls, 5-15 s latency, outside-source citation risk and unknown Gemma free-tier rate limits. [evidence: measured: retrieval_eval.py, abstain_probe.py; https://arxiv.org/html/2407.16833; https://arxiv.org/html/2401.15884; https://ai.google.dev/gemini-api/docs/pricing]

## Findings
- [high] *Retrieval: contextual retrieval and hybrid*: Anthropic, metric 1 - recall@20 (top-20 failure rate): embeddings 5.7%; contextual embeddings 3.7% (-35%); contextual embeddings + contextual BM25 2.9% (-49%); plus Cohere rerank 1.9% (-67%). Context is 50-100 tokens per chunk from Claude 3 Haiku, about $1.02 per million document tokens with prompt caching. They retrieve 150 and rerank to 20 (top-20 beat top-10 and top-5). For knowledge bases under 200k tokens they say to skip RAG and put everything in the prompt. [evidence: https://www.anthropic.com/news/contextual-retrieval]
- [high] *Retrieval: BM25 vs dense (BEIR)*: BEIR (18 datasets, 10 systems): BM25 is 'a robust baseline'; re-ranking and late-interaction models score best on average 'at high computational costs'; dense retrievers 'often underperform' zero-shot. [evidence: https://arxiv.org/abs/2104.08663]
- [high] *Retrieval: RRF k=60*: RRFscore(d) = sum over rankings of 1/(k + rank). k=60 was fixed in a pilot and found near-optimal but 'not critical': pilot MAP .2072 at k=0, .2145 at k=60, .2098 at k=500. RRF beat Condorcet and the best single system by 4-5% on average; on LETOR 3, MAP 0.6051 vs 0.5846 for the best learning-to-rank method (ListNet). [evidence: http://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf (text via pdftotext)]
- [medium] *Retrieval: hybrid vendor benchmarks*: Microsoft whitepaper (PDF created 2025-01-16), average NDCG@3 over 3 internal datasets with text-embedding-3-large 3072-d: text 42.6, vector 46.0, hybrid 51.2, hybrid + new semantic ranker 72.3, + query rewrite 72.8. On BEIR (NDCG@10) vector 54.6 beat hybrid 53.0, so hybrid does not win everywhere. On 'codeword' queries text scored 36.2 vs vector 17.4. The semantic ranker scores 50 docs of 2,048 tokens in 158 ms on their GPU stack. Elastic (2023-07-20): RRF of BM25 + ELSER gave +1.4% vs ELSER and +18% vs BM25 in average BEIR NDCG@10 untuned; a tuned linear blend needs about 40 labelled queries to beat RRF. [evidence: https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/final/en-us/microsoft-brand/documents/ai-search-query-engine-performance-whitepaper.pdf; https://www.elastic.co/search-labs/blog/improving-information-retrieval-elastic-stack-hybrid]
- [high] *Retrieval: RRF vs convex combination*: Bruch et al.: convex combination of normalised scores beats RRF both in-domain and out-of-domain; RRF is 'sensitive to its parameters'; the convex combination can be tuned with few samples. [evidence: https://arxiv.org/abs/2210.11934]
- [medium] *Retrieval: rerankers*: Rerankers help in hosted or large settings: Anthropic 2.9% to 1.9% failure with Cohere; Ask Astro about 13.5% more questions improved after hybrid + Cohere Rerank (100-300 candidates to 8). sbert MS MARCO cross-encoders: MiniLM-L6 NDCG@10 74.30, 1,800 docs/s; L12 74.31, 960 docs/s (hardware not stated). bge-reranker-v2-m3 is 0.6B and multilingual, with no numbers in the card text. On OLake, small open cross-encoders reduced Hit@1 (measured). Cohere billing: one search unit is one query plus up to 100 docs; documents over 500 tokens (with the query) are split and counted separately. The pricing page shows no per-search price. Current models are rerank-v4.0-pro/fast and v3.5. [evidence: https://www.astronomer.io/blog/ask-astro-enhanced-retrieval-augmented-generation-cohere-rerank/; https://www.sbert.net/docs/cross_encoder/pretrained_models.html; https://huggingface.co/BAAI/bge-reranker-v2-m3; https://docs.cohere.com/docs/rerank-overview; https://cohere.com/pricing; measured: scripts/retrieval_eval.py (see measurements)]
- [high] *Retrieval: query rewriting*: HyDE, TREC DL19 nDCG@10: BM25 50.6, Contriever 44.5, HyDE 61.3 (DL20: 48.0 / 42.1 / 57.9) vs fine-tuned ContrieverFT 62.1 / 63.2. The gain is relative to an unsupervised encoder and costs one LLM call before retrieval. Query2doc lifts BM25 by 3-15%. Step-back (PaLM-2L): +7% MMLU Physics, +11% Chemistry, +27% TimeQA, +7% MuSiQue. RAG-Fusion multi-query gives more comprehensive answers, but some drift off-topic when generated queries diverge. [evidence: https://arxiv.org/abs/2212.10496; https://arxiv.org/pdf/2212.10496 (Table 1 via pdftotext); https://arxiv.org/abs/2303.07678; https://arxiv.org/abs/2310.06117; https://arxiv.org/abs/2402.03367]
- [high] *Retrieval: corrective and agentic loops*: CRAG uses a T5-large evaluator (about 0.77B) with upper/lower thresholds: Correct (refine), Incorrect (web search), Ambiguous (both). Generation-only time per instance on PopQA: RAG 0.363 s, CRAG 0.512 s, Self-RAG 0.741 s, Self-CRAG 0.908 s. Gains vs RAG: PopQA +7.0, Biography +14.9, PubHealth +36.6, ARC +15.4. Self-RAG (7B/13B, reflection tokens) claims citation-accuracy gains. Adaptive-RAG routes questions by complexity. [evidence: https://arxiv.org/html/2401.15884; https://arxiv.org/abs/2310.11511; https://arxiv.org/abs/2403.14403]
- [high] *Retrieval: RAG vs long context*: Li et al. 2024: long context beats RAG on average (Gemini-1.5-Pro 49.70 vs 37.33; GPT-4o 48.67 vs 32.60). Self-Route (RAG first, long context when the model says it cannot answer) scores 46.41 / 48.89 using 38-61% of long-context tokens (top-5, 300-word chunks). 'Lost in the Middle': accuracy drops when the relevant text sits mid-context. The OLake docs are about 270k est. tokens, above Anthropic's 200k 'just stuff it' threshold. [evidence: https://arxiv.org/html/2407.16833; https://arxiv.org/abs/2307.03172; https://www.anthropic.com/news/contextual-retrieval]
- [medium] *Chunking: size studies*: Chroma (2024-07-03; 5 corpora, 472 queries; token-level recall/IoU): Recursive 800/400 recall 85.4, IoU 1.5; 400/0 recall 89.5, IoU 3.6; 200/0 recall 88.1, precision 7.0, IoU 6.9; ClusterSemantic 200 best IoU 8.0; LLM chunker best recall 91.9; overlap hurts IoU; the OpenAI Assistants default (TokenText 800/400) has the lowest precision. LlamaIndex (2023, about 20 questions, one 10-K): 1024 tokens was best. NVIDIA (2025-06-18): page-level chunking had the best average accuracy, 0.648 vs 0.603-0.645 for token-based; factoid queries suit 256-512 tokens, analytical ones 1024 or page-level. [evidence: https://www.trychroma.com/research/evaluating-chunking; https://www.llamaindex.ai/blog/evaluating-the-ideal-chunk-size-for-a-rag-system-using-llamaindex-6207e5d3fec5; https://developer.nvidia.com/blog/finding-the-best-chunking-strategy-for-accurate-ai-responses/]
- [high] *Chunking: markdown and code*: LangChain MarkdownHeaderTextSplitter puts header text into metadata (strip_headers defaults to True) and suggests RecursiveCharacterTextSplitter after it for size; overlap never crosses sections. LlamaIndex MarkdownNodeParser toggles an in-code flag on ``` lines so '#' inside code never splits, and attaches header_path. It only recognises backtick fences, and an unclosed fence stops all later splitting. [evidence: https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter; https://developers.llamaindex.ai/python/framework-api-reference/node_parsers/markdown/]
- [medium] *Chunking: contextual headers and small-to-big*: dsRAG KITE benchmark (LLM-graded 0-10): top-k 4.72; contextual chunk headers 6.04; relevant segment extraction 6.73; both 8.42. LlamaIndex auto-merging (2048/512/128) was 'roughly the same' as baseline (correctness 4.27 vs 4.21; pairwise 52.5%). On OLake, breadcrumb headers gave +11-14 points Hit@1 (measured). [evidence: https://github.com/D-Star-AI/dsRAG; https://developers.llamaindex.ai/python/examples/retrievers/auto_merging_retriever/; measured: scripts/retrieval_eval.py]
- [high] *OLake corpus: raw MDX vs rendered HTML*: Ingest rendered HTML. 20 of 125 published pages render shared snippets via global MDX component tags (text absent from raw MDX), 6 with JSX config tables. In rendered HTML, inactive Docusaurus tabs are present as hidden tabpanels, headings carry ids for #anchor links, and shared snippet content (e.g. Postgres SSL modes) appears. The REST catalog page holds 8 catalogs as tabs with repeated headings, so the tab label must go into the breadcrumb. Many H1s are just 'Overview', so take the trail from the breadcrumb nav. [evidence: measured: scripts/shared_usage.py and corpus_stats.py on sparse clone datazip-inc/olake-docs @ d060071; measured: curl https://olake.io/docs/connectors/postgres/ (grep tabpanel / h2 ids); https://github.com/datazip-inc/olake-docs]
- [high] *OLake corpus: HTML parsing pitfall*: olake.io production HTML is minified with optional end tags omitted: on the REST catalog page, 371 '<li' vs 172 '</li>' and 278 '<p' vs 14 '</p>'. Python's html.parser mis-nests these, so tab labels came out concatenated; lxml parses them correctly. Code blocks are div.token-line per line and must be re-joined with newlines. [evidence: measured: python count on crawled HTML; scripts/debug_tabs.py with html.parser vs lxml]
- [high] *OLake site: links and freshness signals*: olake.io is served by GitHub Pages (server: GitHub.com, cache-control max-age=600).
