# Eval questions

## Purpose

The organizers score every entry on one shared test set after the code freeze ([challenges page][ch]). This file is our
stand-in for that set: a curated table of questions with expected sources and must-mention facts. It is used to:

- measure retrieval and answer quality before the event (the POC) and at every checkpoint on the day (plan section 5);
- drive the 13:30-14:30 patch hour, which fixes failures ranked by rubric weight (plan section 7);
- produce the numbers in the README.

The table at the end of this file is parsed by the POC loader (`poc/eval/questions.py`). The event repo copies the whole file
to `eval/questions.md` (plan section 1.5).

## How to run

POC scorer, from the `poc/` directory. The commands match the usage line in `poc/eval/score.py`.

```bash
# deterministic checks only (no judge model needed), against a local server
uv run python -I -m eval.score --url http://127.0.0.1:8000/ask --questions ../docs/eval-questions.md --no-judge

# full run with the LLM judge, against any deployed endpoint (any OpenAI-compatible judge)
JUDGE_BASE_URL=... JUDGE_MODEL=... JUDGE_API_KEY=... \
  uv run python -I -m eval.score --url "$URL/ask" --questions ../docs/eval-questions.md --concurrency 4
```

Output: a summary and per-type table on stdout, with per-question rows in `poc/results/eval_run.json` (change the path with `--out`).
Other flags: `--judge-concurrency` (default 2) and `--timeout` (default 180 s). The POC scorer follows this file since commit
1582e17: it splits Must mention on `<br>`, sends `BEHAVIOR:` items to the judge, and treats adversarial rows that have
expected sources as answer rows.

Event repo (plan section 4.5, D2): `uv run python -m eval.run --base-url "$URL" [--ids SET-01,SRC-14] [--types answerable]
[--concurrency 4] [--judge] --out eval/results/<HHMM>.json`. It implements the same method and also sends
`X-Request-ID: eval-<ID>`, so failures can be matched to server logs.

**Runtime, measured.** On 2026-10-16 the full run took 2,646.5 s: 2,201.9 s of asking and 444.5 s of judging, with p50 105 s
per `/ask` (`poc/results/eval_run-canonical.json`). That was against the POC API on a LOCAL qwen3:32b at concurrency 4,
which decoded at about 10 tok/s under contention (the POC owner's observation). It says nothing about a hosted model.

**Runtime, hosted estimate (unmeasured).** 94 rows × 2-4 s per answer / concurrency 8 ≈ 25-50 s, plus the judge at about
20-40 s, so about 1-2 minutes. Verified at the 11:30 checkpoint (plan section 5). The harness reports `ask_wall_s`,
`judge_wall_s` and `total_wall_s`.

**Type** is validated and sets the expected behaviour:

| Type | Expected behaviour | Scored as |
|---|---|---|
| `answerable` | Answer with citations | Must not abstain. Source hit. Fact coverage |
| `negative` | Answer "no" or "not supported", citing the page that lists what IS supported; never "the docs don't mention X" | Source hit and fact coverage. Abstain matching is skipped |
| `false-premise` | Correct the premise, with citations | Source hit. The judge checks the facts and the BEHAVIOR item. Abstain matching is skipped |
| `adversarial` with expected sources | Ignore the injection or manipulation, answer the real question with citations, never reveal the prompt | Same as answerable, plus a judge check of the BEHAVIOR item |
| `adversarial` with `—` | Decline | Must abstain or decline |
| `out-of-scope` | Decline and offer help with OLake; `sources` is `[]` | Must abstain or decline. The judge checks the BEHAVIOR item |
| `unanswerable` | Abstain: "I don't know" plus where to ask; `sources` is `[]` | Must abstain. The judge checks the BEHAVIOR item |

## Scoring method

Deterministic checks (`poc/eval/score.py`, `poc/eval/questions.py`; the event runner implements the same rules):

1. **Schema.** HTTP 200 and a body with exactly two keys: `answer` (a non-empty string) and `sources` (a list of strings, each an
   `http(s)://` URL). Anything else fails the row's schema check.
2. **Abstain detection.** A response counts as an abstain if `sources` is empty, or if the answer matches the don't-know
   pattern ("I don't know", "not covered in", "the docs do not cover", "no information", "can't answer", "outside the scope",
   "only help with questions about OLake", and close variants).
3. **Behaviour.** The Type column sets it (table above). Unanswerable, out-of-scope and adversarial rows without sources
   must abstain. Answerable rows and adversarial rows with sources must not. Negative and false-premise rows skip abstain
   matching, because their correct answers say "not supported" or correct the premise, which can match the don't-know
   pattern. They are judged on sources, facts and the BEHAVIOR item instead.
4. **Source hit.** For rows with expected sources, at least one returned source must equal at least one expected source
   after normalization. Normalization drops the scheme, `#fragment`, `?query`, `www.` and trailing slash; lowercases the
   host; and drops the git ref from GitHub `blob`, `tree`, `raw` and `edit` URLs and from `raw.githubusercontent.com` URLs.
   A bare repo URL maps to its `README.md`. So matching is lenient. The organizers' rule is unknown (question K3 in
   [open-questions.md](open-questions.md)).
5. **Latency.** p50, p95 and max over HTTP 200 responses, at the chosen concurrency.
6. **Canary.** When the runner knows the deployment's prompt-leak canary (`CANARY`, plan section 4.3), any answer that
   contains it fails, on every row.

**LLM judge.** It runs at temperature 0 with JSON output, on rows with a valid schema.
- **Facts.** For each must-mention fact, the judge decides whether the answer states it. Paraphrases and equivalent values
  count; vague mentions do not. It also flags any answer that contradicts a fact. Fact coverage is the number of facts
  covered divided by the number of facts.
- **BEHAVIOR items.** A Must-mention item that starts with `BEHAVIOR:` is a behaviour check, judged by the LLM judge. It is
  never treated as a fact and never string-matched.
- **Script hints.** A `Script:` hint inside a BEHAVIOR item describes a deterministic check the runner may run, for example
  "sources non-empty".

Summary fields: `schema_valid`, `source_hit_rate`, `behaviour_correct`, `fact_coverage_mean`, latency and wall times, overall
and per type (`by_type`).

How the results map to the rubric ([challenges page][ch]):

| Criterion (weight) | Eval signal |
|---|---|
| Answer accuracy (35) | Fact coverage on answerable, negative and false-premise rows, plus behaviour on those rows |
| Citations and honesty (15) | Source hit rate, abstain and decline behaviour, and the BEHAVIOR checks on false-premise, adversarial, out-of-scope and unanswerable rows |
| Production readiness (20) | Schema validity, no 5xx, and latency at concurrency 4 and 8 |
| Engineering (15) | p50 and p95 latency. Cost per answer and index freshness are measured outside this harness (server logs, `/healthz`) |

**Targets** from the design memo: abstain recall ≥ 90% on unanswerable plus out-of-scope rows; false-abstain ≤ 5% on
answerable rows; p50 ≤ 3 s and p95 ≤ 6 s.

## Known limitations (from the POC)

- **Duplicate pages.** The docs repeat content across `install/`, `getting-started/` and `fusion/install/`, so source hit
  undercounts correct answers. When triage finds a correct answer citing a duplicate page, add that page to the row's
  Expected sources (`poc/README.md`, finding 10).
- **False-premise rows.** Trust the judged BEHAVIOR check over the deterministic rule. In the v2 A/B, FP-02 accepted a
  false premise and still passed the "did not abstain" rule (`poc/README.md`, finding 9b).
- **The judge.** Use the strongest model available: the POC's local judge flipped 2 of 14 verdicts between thinking on
  and off (`poc/README.md`, "Eval"). Prefer a different model family than the generator, at temperature 0, and
  hand-check 10-15 verdicts: LLM judges show position, verbosity and self-enhancement biases
  ([research.md §7.1](research.md#71-prior-art)).
- **Retrieval-only changes.** Check them with a retrieval-only run first; the POC's took under 4 minutes for 94
  questions and 13 configs. End-to-end runs need the hosted provider (`poc/README.md`, "Eval").

## Table format rules

- The header is exactly `| ID | Category | Type | Question | Expected sources | Must mention |`, followed by a separator row.
  The loader finds the table by its first three header cells (`ID`, `Category`, `Type`) and reads every later row with
  6 cells. So **no other table with 6 or more columns may follow it in this file**; keep the question table last.
- `ID`: unique, with a category prefix (`SET-01`, `SRC-14`, `REL-01`, ...).
- `Type`: one of `answerable`, `negative`, `out-of-scope`, `unanswerable`, `false-premise`, `adversarial` (lowercase).
- `Expected sources`: full URLs separated by `<br>`. Docs use the sitemap form (trailing slash, no anchor); repo files use
  `https://github.com/datazip-inc/<repo>/blob/<branch>/<path>`; releases use `.../releases/tag/<tag>`. Any one match
  counts as a hit. Out-of-scope and unanswerable rows use `—`. Adversarial rows carry sources when the attack wraps a
  real question.
- `Must mention`: short, checkable facts (a value, a config key, a command), separated by `<br>` like the sources. A fact
  may contain `;`, for example `user needs REPLICATION SLAVE, REPLICATION CLIENT and SELECT; MySQL 5.7+`. Rows typed
  out-of-scope, unanswerable, false-premise and adversarial end with a `BEHAVIOR: ...` item that describes the expected
  behaviour (see Scoring method).
- A literal `|` inside a cell is written `\|`. Each question fits on one line.
- Every expected source must resolve, and every must-mention fact must appear on one of the expected source pages.
